## The answer, before the detail

**28 of 88 rows (32 %) are named by an issue that carries the marker; 60 are not.** The join itself is clean — no row is claimed twice, no marker names a row the register does not have — so the shortfall is population, not duplication.

An issues-first regeneration would therefore cover at most those rows and would drop every column an issue cannot answer: `agreement_quote`, `pdf_pages`, `approval_jaden`, `approval_walt`. **The register is the record; issues are the delivery layer joined onto it by one key.**

## The marker contract a backfill would have to honour

One HTML comment, in the issue body, on the first line of it:

```html
<!-- spec-row:APP-05 -->
```

The key is the register's `id` cell, byte for byte. `lib/spec/issues.ts` matches it with `/<!--\s*spec-row:\s*([A-Za-z0-9._-]+)\s*-->/` and says why in its own words: *"the marker is the key, never a title and never a label … a body without one is skipped and counted, never guessed at from its text: a heuristic that reads a title is a parser this repo has already been burned by, and it fails silently on the day someone edits a title."*

A title match is refused for three reasons this repository has already paid for: a retitle silently unjoins the row, two rows can share a title fragment, and the fallback is invisible — the register would simply lose a column with no error anywhere. A marker is editable text a human can see and a script can prove.

The read is one call — `labels=spec&state=all&per_page=100` — so a new issue must carry the `spec` label and a `tier/R1|R2|Later` label to be read as the register expects, and a 101st issue would return a full page the read refuses rather than truncates.

One trap, measured rather than imagined. The issue that carries *this* report described the marker syntax in its own prose, inside backticks, and the run joined it as a row id of `ID` — no register row has that id, so the page drew nothing while the count of marker-bearing issues read one too high. Backticks are not an escape: the pattern reads the raw body, and `specIssueOf` never checks the id it finds against the register. The issue was reworded, so this run is clean — but nothing in the parser changed, and the next author who documents the syntax re-creates it.

**The contract needs a shape rule, not only a pattern.** A marker should be the first line of the body, alone on its line. That is already how every issue in this batch writes it: 28 of 28 are the first line, 0 sit alone but not first, and 0 sit inline in prose. A first-line rule therefore costs nothing today and makes "an issue that talks about the marker" and "an issue that claims a row" two different things — which is the difference between a number and a claim. Escaping the example in a code span would work too, but it puts the guarantee in the author's hands rather than the parser's, and the parser is the thing that never forgets.

## The decision this leaves

**Declare the register authoritative for the delivered rows; do not backfill them.** The numbers make the case on their own: 0 of the 60 uncovered rows is delivery work, so a backfill of 60 issues would create 60 closed issues — 47 recording a delivery the register already states and a code path already evidences, 13 recording a non-obligation the agreement's own wording already carries. Nothing they add changes the derived reading — a closed issue on a Delivered row derives the status the row already declares.

What a backfill would cost, and what it would buy:

| option | issues created | effort | what changes on the surface |
| --- | --- | --- | --- |
| backfill the 60 | 60, every one closed | a generator run (~15 min) plus a read of 60 bodies, an hour or two | coverage 28 → 88, and 60 derived readings identical to the declared ones |
| declare authoritative | 0 | ~1 h to write the rule beside `lib/spec/issues.ts` and test the four degenerate cases, plus the first-line shape rule and its test | coverage stays 28 of 88; the other 60 draw the "no linked issue" state |

The failure mode is already visible in the 28: 7 closed issues sit on rows the register still calls Partial or Tentative. Closing an issue does not move the register, and creating more issues does not either. The one thing that would move it is fixing those rows — and that is a human decision per row, not a backfill.

If the owner wants a GitHub-visible record for the rows where the counterparty is the audience rather than the team — the `B-01`–`B-12` beyond-agreement deliverables — that is 12 closed issues, not 60, and this page should be regenerated to carry them.

## How to re-run this page

```bash
node scripts/spec-register-coverage.mjs          # reads the register and every issue, writes both files
pnpm docs:nav                                    # the hub row and the nav block are generated, not authored
```

`SPEC_VALIDATION_CSV` points the run at a different copy of the register; `SPEC_COVERAGE_REPO` at a different repository. The run needs the network and the CSV, which is why it is a report and not a gate step: it fails loudly here rather than turning every CI run red. It stops without writing when `gh` cannot answer, when the repository returns no issues, or when not one issue carries a marker — an empty table is the one outcome a silent failure would produce.
