The goal, in your words

«to be able to separate, and develop, or change independent of the webapp user platform.»
Phase 1 · the gateproduct.operator + FLAG_PRODUCT_OPERATOR, 404 not redirect. Value: it enumerates the operator set and can switch it off — you cannot extract a set you cannot list or turn off.
Phase 2 · the seamA typed read contract the operator surfaces must go through (facts, never pg or lib/db/**), one dependency arrow (operator → content/), and a test that fails if either direction breaks. That test is the independence — it survives whichever home you pick.
Later · the moveIn-repo package, own deployment, or own repo — cheap once the seam carries the coupling. Not decided today, and not needed today.

Grill — three questions the ADR cannot answer for you

1. Is the goal the URL disappears for a normal user, or the code leaves this repo? Those buy very different things: a gate is reversible in one flag, a split is permanent maintenance.

2. Does /dashboard/templates stay a product surface? I read your note — "native template creation, versioning, metrics, lifecycle" — as a feature you are building, not dev content. If it is dev content, say so and it changes the whole option.

3. What is the v2-docs-preview deployment for — a design mirror, or the intended future home of the docs? If it is the future home, option C stops being hypothetical.
